# Vibeathon Workbook — Building Voice + Messaging Agents on TAC

A hands-on guide for building a working conversational AI agent on top of **Twilio Agent Connect (TAC)** in a half-day vibeathon. Pick a use case, write a prompt, wire two tools, and ship something that actually answers WhatsApp messages by lunch.

This workbook is **self-directed** — read the chapter intros, jump to whichever path matches your build. The suggested order is end-to-end, but every chapter is independently useful.

> **Setup assumed done as pre-work.** This workbook starts after you've cloned the template, filled in `.env`, run `npm install`, and confirmed `npm run dev` boots cleanly. If any of those aren't true, finish setup first — see `README.md`.

## Before you start

### Verify your starting point

Run these checks. If any fail, stop and fix before continuing.

```bash
# In the template directory
npm run dev
```

You should see a "Server listening on port 3000" (or whatever port) message. From another terminal:

```bash
curl -s http://localhost:3000/health
```

Expected: a 200 with a small JSON body. If you get connection refused, the server didn't start — check the logs in the first terminal.

Now send a WhatsApp message to your configured WhatsApp Sender number. Watch the first terminal's logs. You should see:
- An inbound message event
- A response generated by the LLM
- An outbound message sent back

If you don't get a reply on WhatsApp, check the gotchas in [Appendix B](#appendix-b--stuck-common-issues).

### What you'll build

By the end:
- A custom agent with a focused persona and a clear scope
- One or two tools the agent uses (KB search at minimum, optionally a memory write or a custom data lookup)
- A working WhatsApp conversation that recalls customer history and hands off to a human when needed
- Optional: voice support, deployment, Conversation Intelligence observability

The deliverable doesn't have to be polished — vibeathons reward exploration. Aim for "I learned how the parts fit together" over "this is production-ready."

## Chapter 1 — Pick your use case

Pick a scenario that matches something you'd actually want to demo to a customer. The workbook ships five starter kits in [Appendix A](#appendix-a--starter-kits-in-detail):

| Kit | One-liner | Why it's good for a vibeathon |
|---|---|---|
| **Customer support FAQ** | Generic helpdesk with a product KB | Simplest. KB-only, no memory writes needed. |
| **Sales SDR** | Qualifies leads, captures interest, schedules follow-up | Tests memory writes + handoff. Touches more of the surface. |
| **Debt collection / cobrança** | Answers payment questions; hands off for negotiation | Compliance-aware prompt; great for regulated industries. |
| **Appointment scheduling** | Books / reschedules slots against a calendar | Forces you to write a custom tool (calendar API). |
| **Internal IT helpdesk** | Handles common IT tickets; opens a Jira ticket otherwise | Mixes KB with a write-back system. |

If your customer engagement maps to none of these — pick the closest and rebrand. The patterns transfer.

### What pick-and-go looks like

Open Appendix A. Find your kit. It has:
- A 1-paragraph scenario (so you know what the agent is for)
- A KB content checklist (what to seed the knowledge base with — bring your own KB content from the customer, or use the sample)
- A prompt skeleton (the starting point you'll customize)
- A tool list (what you'll wire — usually 2-3 tools)
- A "demo path" (the conversation flow you'll show)

Copy the prompt skeleton into `src/prompts/systemPrompt.md`, the tool list and demo path you can keep open in another tab. Now you're ready for Chapter 2.

### Checkpoint

You've picked a kit, copied the prompt skeleton into `systemPrompt.md`, and you can describe in one sentence what your agent does.

## Chapter 2 — Write the system prompt

The system prompt is where 80% of your agent's behavior lives. The model is good; what you put in the prompt is what makes the difference between "useful agent" and "chatbot that's vaguely on-topic."

### Anatomy of a working TAC prompt

The patterns below come from production-shaped builds. You don't need all seven — but you'll regret skipping any.

#### 1. Language enforcement (one line, very top)

```markdown
- Todas as respostas DEVEM ser em Português do Brasil (pt-BR).
```

Or whatever your locale is. LLMs drift to English on technical reasoning. Make this the FIRST line of the prompt, no other content above it.

#### 2. Persona + objective (1-2 paragraphs)

```markdown
## Objetivo
Você é **Marina**, assistente da **ACME Bank**. Atende clientes pelo WhatsApp
(e por voz, quando preferirem) com dúvidas sobre cartões, empréstimos, e
contas correntes.
```

Name the agent. Name the company. State the scope. **Don't be vague** — "I help with all your needs" is meaningless to the LLM.

#### 3. Channel awareness (~10 lines)

```markdown
## Channel Awareness
O canal atual é informado em mensagem de sistema (`Current communication
channel: <channel>`).

Adapte o estilo:
- **`voice`**: frases curtas, sem markdown, soletre números longos
- **`whatsapp` / `sms` / `chat`**: markdown leve OK, emojis com moderação
```

If you're voice-only or messaging-only, simplify this.

#### 4. Customer identity via Memora (~5 lines)

```markdown
## Identidade do cliente
- Use o `firstName` do trait `Contact` quando natural — saudação, momentos
  importantes. **NÃO prefixe toda mensagem com o nome do cliente** (soa
  robótico).
- Não peça dados que já estão na memória.
- Se a memória mostrar interação anterior, traga à tona naturalmente.
```

The `[Memory]` block gets injected automatically — your prompt just tells the model how to use it.

#### 5. Tools section (1 subsection per tool)

```markdown
### 1. Dúvidas sobre produtos (`search_acme_kb`)
- Para QUALQUER pergunta factual sobre produtos, taxas, prazos, condições,
  chame `search_acme_kb` ANTES de responder.
- Use os números da KB **verbatim** — não arredonde.
- Se a KB não tiver resposta, encaminhe via `liveAgentHandoff`.
```

**Be specific about triggers.** "Use it for X" beats "use it when relevant." Name the tool exactly as it will be exposed.

#### 6. Tone + posicionamento (3-5 bullets)

```markdown
## Tom
- Acessível e direta. Trate o cliente bem, vá ao ponto.
- Educativa, não comercial. Quem recomenda é o assessor humano.
- Honesta sobre limites. Se algo é assessoria personalizada, encaminhe.
```

Tone bullets are what make the agent sound like the brand. Steal liberally from the customer's existing brand guidelines.

#### 7. Restrições (the load-bearing part)

```markdown
## Restrições
- Nunca dê recomendação personalizada (regulação CVM).
- Nunca prometa rentabilidade garantida.
- Não invente valores, taxas, prazos. Use a KB ou encaminhe.
- Respeite a LGPD. Não confirme dados sensíveis a quem não autenticou.
```

This is where you stop the agent from saying things that get the customer sued. Compliance bullets are not optional for regulated industries.

### Iteration loop

The fastest way to improve a prompt is to **read the agent's responses** and add a constraint each time it does something wrong.

```bash
# Terminal 1: server running
npm run dev

# Terminal 2: watch logs
# (the dev script already pipes to pino-pretty — just read terminal 1)
```

Send a message from WhatsApp. Read the response. If the agent did something off — too verbose, used the customer's name 7 times, made up a number — add ONE constraint to the prompt and reload.

> **Tip**: `tsx watch` auto-reloads the prompt file. You don't have to restart.

### Common prompt smells

| Smell | Fix |
|---|---|
| Agent ends every message with the customer's name | Add the "don't prefix every message with the name" rule (Chapter 4) |
| Agent says "I'd be happy to help with..." in every response | Add: "responda direto, sem floreio" |
| Agent uses English mid-conversation | Make sure language line is at the very top, before anything else |
| Agent uses markdown / asterisks on voice | Strengthen the voice section: "Sem markdown, asteriscos, ou emojis em respostas de voz." |
| Agent makes up product details when the KB is empty | Add: "Se a KB não retornar resposta, NÃO INVENTE. Encaminhe via handoff." |
| Agent answers "I don't know" instead of using the KB | Add: "Use SEMPRE search_X_kb antes de dizer que não sabe." |

### Checkpoint

Send a WhatsApp message. The agent responds in your language, in your brand voice, with the persona name. The response is the right length for the channel.

## Chapter 3 — Wire your first tool: KB search

The KB search tool unlocks 80% of the agent's usefulness. Most factual questions go through here. If your KB is set up, this chapter is straightforward.

### Two paths

The template supports four LLM providers, and they fork on tool wiring:

| Provider | Tool wiring |
|---|---|
| `openai-chat-completions`, `openai-responses`, `openai-agents` | TypeScript via `createKnowledgeSearchTool` from `twilio-agent-connect` |
| `langflow` | Python Custom Component inside the Langflow flow |

Both end up with a tool the agent can call. Pick the path matching your `LLM_PROVIDER` setting.

### Path A: openai-* (TypeScript)

In `src/index.ts`, add a `buildDynamicTools` callback to your `createApp` call:

```typescript
import { createKnowledgeSearchTool, type TAC, type TACTool } from 'twilio-agent-connect';

const KB_ID = process.env.KB_ID;

function buildDynamicTools(tac: TAC): TACTool[] {
  if (!KB_ID) {
    console.warn('[startup] KB_ID not set — KB search tool not registered.');
    return [];
  }
  const knowledgeClient = tac.getKnowledgeClient();
  if (!knowledgeClient) return [];

  return [
    createKnowledgeSearchTool(knowledgeClient, KB_ID, {
      name: 'search_acme_kb',
      description:
        'Busca na base de conhecimento da ACME (produtos, taxas, prazos, ' +
        'condições). Use SEMPRE antes de responder pergunta factual. Se a ' +
        'busca não retornar resultado útil, encaminhe via liveAgentHandoff.',
      topK: 5,
    }),
  ];
}

createApp({
  systemPrompt,
  tools: allTools,
  buildDynamicTools,  // ← add this line
  welcomeGreeting: '...',
}).catch(...);
```

Add `KB_ID=know_knowledgebase_...` to your `.env`. Restart the server.

### Path B: Langflow (Custom Component)

Open your Langflow flow in the browser. Add a Custom Component, switch to the Code tab, paste the contents of `tac-fork/getting_started/examples/langflow/flow/components/twilio_knowledge_search.py` (or wherever your team keeps shared components).

Wire its inputs:
- `twilio_api_key_sid` → Global Variable `TWILIO_API_KEY_SID`
- `twilio_api_key_secret` → Global Variable `TWILIO_API_KEY_SECRET`
- `knowledge_base_id` → your KB ID (e.g., `know_knowledgebase_...`)
- `tool_name` → `search_acme_kb` (match your prompt)
- `tool_description` → same wording as Path A

Connect the Tool output to the Agent component. Save the flow.

### Test that it fires

In your prompt, you should already have:

> Para QUALQUER pergunta factual sobre produtos, taxas, prazos, condições, chame `search_acme_kb` ANTES de responder.

WhatsApp the agent a question that requires KB knowledge ("o que é o Cartão Mais?", "qual a taxa do empréstimo X?"). In your server logs, you should see:

```
[tool] search_acme_kb invoked with { query: "..." }
[tool] search_acme_kb returned N chunks
```

The agent's response should now contain content from the KB, not hallucinations.

### Common issues

- **Agent doesn't call the tool** — your prompt's trigger language is too vague, OR the tool name in the prompt doesn't match the wired name. Check both.
- **Tool fires but returns 0 chunks** — KB ID wrong, or the KB is empty. Verify by checking the KB in the Twilio Console.
- **Tool fires but the agent still hallucinates** — add to the prompt: "Use APENAS os números/textos que vieram da KB. Não invente."

### Checkpoint

Ask the agent a question that needs KB content. The response uses real KB content, not invented numbers. The tool fires (visible in logs).

## Chapter 4 — Memory: the customer remembers you

The agent already gets a `[Memory]` block injected on every turn with the customer's traits + recent observations + summaries. You don't have to wire that — it's automatic via TAC + Memora.

What you DO want to wire:
1. **Greet by name** (no code needed — just prompt wording)
2. **Write observations** when something noteworthy happens (custom tool)

### Greet by name (no code)

Make sure your prompt has the identity section from Chapter 2:

```markdown
## Identidade do cliente
- Use o `firstName` do trait `Contact` quando natural — saudação, momentos
  importantes. **NÃO prefixe toda mensagem com o nome do cliente** (soa
  robótico).
```

Test: send "oi" from a phone whose profile already has a name in Memora. The agent should greet you by first name.

If your profile is empty (new phone), the agent won't have a name to use. That's expected — you'd handle this case with a "register name" tool (see the inter-cx-event reference build for an example).

### Write observations (custom tool)

Observations are the persistent notes the agent leaves for "future me." When the customer says "vou pensar nesse CDB", you write that, and next conversation the agent recalls it.

#### Path A: openai-* (TypeScript)

Add a tool via `defineTool` that POSTs an observation. The pattern:

```typescript
import { defineTool, type TACTool } from 'twilio-agent-connect';

const recordInterestTool: TACTool = defineTool(
  'record_customer_interest',
  'Use quando o cliente sinalizar interesse em produto ou próxima ação ' +
  '("vou pensar nesse CDB", "me manda mais detalhes"). Recebe uma frase ' +
  'factual descrevendo o sinal.',
  {
    type: 'object',
    properties: {
      customer_phone: { type: 'string', description: 'E.164' },
      signal: { type: 'string', description: 'Frase factual, passado/presente' },
    },
    required: ['customer_phone', 'signal'],
  },
  async ({ customer_phone, signal }, { tac }) => {
    const memory = tac.getMemoryClient();
    if (!memory) return 'Memory client unavailable.';

    const lookup = await memory.lookupProfile('phone', customer_phone);
    if (lookup.profiles.length === 0) return 'No profile for this phone.';
    const profileId = lookup.profiles[0]!;

    // POST observation directly (SDK has a body-shape bug in some versions)
    const storeId = memory.getStoreId();
    const cfg = tac.getConfig();
    const auth = 'Basic ' + Buffer.from(`${cfg.apiKey}:${cfg.apiSecret}`).toString('base64');

    await fetch(
      `https://memory.twilio.com/v1/Stores/${storeId}/Profiles/${profileId}/Observations`,
      {
        method: 'POST',
        headers: { 'Content-Type': 'application/json', Authorization: auth },
        body: JSON.stringify({
          observations: [{
            content: signal,
            source: 'my-app',  // ← your app's source tag
            occurredAt: new Date().toISOString(),
          }],
        }),
      },
    );

    return 'Observation recorded.';
  },
);

// then push into the static tools array passed to createApp
```

#### Path B: Langflow

Use `twilio_conversation_memory_observation_writer.py` from the components folder. Same wiring pattern as the KB tool — paste, wire inputs, connect Tool output.

### Observation hygiene (these matter)

The wording of observations matters a lot because they get recalled across conversations.

| Do | Don't |
|---|---|
| Past tense, factual: "Cliente perguntou sobre CDB Mais Limite em 22/05" | Pending state: "Aguardando o cliente decidir" |
| Include date for temporal anchoring | Implicit "now" — future-agent doesn't know when "now" was |
| Set a clear `source` like `my-app-interest` | Default to no source — cleanup later becomes impossible |
| Build a cleanup script EARLY | Wait until observations pile up across testing |

A bad observation will poison future conversations. Be intentional.

### Test it

1. From WhatsApp: "tô pensando em pegar o CDB Mais Limite"
2. Watch logs — should see `record_customer_interest` fire.
3. End the conversation (close it manually or just walk away — Memora persists).
4. Wait 30 seconds. From the same WhatsApp number, message again: "oi, alguma novidade?"
5. The agent should reference the prior CDB interest unprompted.

### Checkpoint

You've written one observation and confirmed the agent recalls it in a later conversation.

## Chapter 5 — Human handoff

When the agent can't (or shouldn't) handle a request, it hands off to a human in Flex. In Maestro mode this is **auto-wired** — you don't need to register a tool. You just need:

1. `MESSAGING_MODE=maestro` in `.env` (default in this template)
2. `TWILIO_STUDIO_HANDOFF_FLOW_SID=FW...` set to your Studio Flow's SID
3. Your prompt naming `liveAgentHandoff` as the tool

The handoff tool is registered automatically with the name `liveAgentHandoff`.

### Trigger it from the prompt

In your prompt, define when handoff fires. Be explicit:

```markdown
### Quando encaminhar para humano (`liveAgentHandoff`)
Encaminhe sempre que UMA condição for verdadeira:
1. A KB não retornou resposta útil (não invente — encaminhe).
2. O cliente pede recomendação personalizada (regulação).
3. O cliente quer negociar valores específicos ou alterar contrato.
4. O cliente expressa frustração, raiva, ou vulnerabilidade.
5. O cliente pede explicitamente para falar com humano.

Ao chamar, passe:
- `customer_phone` (E.164)
- `customer_name` (da memória, ou o que o cliente informou)
- `reason` (uma frase factual descrevendo o motivo)
```

The clearer your trigger conditions, the more reliably the agent will fire the tool at the right moment.

### Test it

Easiest path: tell the agent "quero falar com um humano" or ask something the KB doesn't cover. Watch:
- The agent should call `liveAgentHandoff`
- The Studio Flow execution should start (visible in Twilio Console → Studio → Flows → Executions)
- If wired all the way through: a Task lands in Flex with the conversation history + `attributes` you set in `HandoffData`

### Common issues

- **Tool fires but Flex task has no context** — your handoff payload is missing `HandoffData.attributes`. Check the Studio Flow's `Send to Flex` widget reads `attributes` via `| to_json`.
- **Tool fires but no Studio execution** — the `TWILIO_STUDIO_HANDOFF_FLOW_SID` is wrong, or the Flow's REST trigger isn't enabled.
- **Tool never fires** — your prompt's trigger conditions are unclear, or you're using `MESSAGING_MODE=conversations-v1` (not Maestro) which uses a different handoff path.

### Checkpoint

Send a message that should trigger handoff. The Studio Flow executes. (Bonus: a Flex task lands.)

## Chapter 6 — Channel awareness

This is where TAC earns its money: the same conversation can move from WhatsApp to voice mid-flow, and the agent remembers everything that happened.

### How channel switches work

When the channel changes (e.g., customer taps a "Falar por voz" button in WhatsApp), TAC injects a system message:

```
Current communication channel: voice
```

The model adapts based on your channel-awareness prompt block. **Important gotcha**: `addSystemContext` is append-only, so the prior `Current communication channel: whatsapp` line stays in the context. Without the right framing, the model anchors on the OLD channel and tells the voice caller to "tap the button" because the WhatsApp framing is still in scope.

The template already injects a "supersede" hint when the channel changes — you don't have to write code for this. But you DO have to make sure your prompt's channel section is in place (Chapter 2, section 3).

### The voice CTA pattern (WhatsApp → in-app voice)

The smoothest cross-channel demo: WhatsApp customer taps a button, an in-WhatsApp voice call starts, agent picks up with full context.

You need:
1. A WhatsApp `twilio/call-to-action` Content Template with a `VOICE_CALL` action button
2. A tool `send_voice_cta` that sends the template
3. Voice routing pointing at your TAC server

**Creating the template** (one-time, via Twilio Content API):

```typescript
// scripts/create-voice-cta-template.ts
const res = await fetch('https://content.twilio.com/v1/Content', {
  method: 'POST',
  headers: { Authorization: 'Basic ' + Buffer.from(`${SID}:${TOKEN}`).toString('base64'),
             'Content-Type': 'application/json' },
  body: JSON.stringify({
    friendly_name: 'my_voice_cta',
    language: 'pt_BR',
    variables: { '1': 'Rafaela' },
    types: {
      'twilio/call-to-action': {
        body: 'Oi {{1}}! Quer continuar por voz? Toque no botão.',
        actions: [{ title: 'Falar com Marina', type: 'VOICE_CALL' }],
      },
    },
  }),
});
const { sid } = await res.json();
console.log('Template SID:', sid);  // ← paste into .env as CONTENT_VOICE_CTA_SID
```

Then write a `send_voice_cta` tool (TS or Langflow Custom Component) that POSTs the template via the Messages API to the customer's phone.

### Test the cross-channel arc

1. WhatsApp the agent. Have a conversation about something specific (a product, a question, anything).
2. Say "tem como falar por voz?"
3. Agent calls `send_voice_cta`. You receive a WhatsApp message with a "Falar com Marina" button.
4. Tap the button. The in-WhatsApp voice call starts.
5. Agent picks up. On its FIRST voice turn, it should reference what you were just discussing on WhatsApp.

That last step is the wow moment. It works because Memora preserves the conversation context across the channel switch.

### Common issues

- **Voice call connects but agent has no context** — check the channel-switch system context is being injected (look in the logs for "Current communication channel" updates).
- **Template send returns 63013** — channel policy violation, usually a Content Template issue. Voice CTA works in-session (24h customer-initiated window) without approval, but make sure the customer messaged you first in the last 24h.

### Checkpoint

You've moved from WhatsApp to voice mid-conversation, and the agent referenced the prior WhatsApp topic on its first voice turn.

## Chapter 7 — Observe what's happening

Once your agent is doing the right thing, you want to know WHY. Conversation Intelligence gives you summaries, sentiment, and custom scoring on every conversation.

### Built-in operators

If you've attached an Intelligence Configuration to your Conversation Configuration, these run automatically:

- **Summary** — short paragraph of what the conversation was about
- **Sentiment** — overall customer sentiment
- **Language** — detected language

Find them in **Twilio Console → Conversation Intelligence → Conversations → [your recent transcript]**.

### Script Adherence

Built-in operator that checks whether the agent followed your playbook. You define categories like:
- "Greeted by first name"
- "Confirmed product + value before executing transaction"
- "Did not promise guaranteed returns"

Each category gets scored `adhered` / `not_adhered` / `not_applicable`. **Six categories is the practical upper bound** — beyond that, per-category quality drops.

Configure via Console → CI → Operators → New → Script Adherence. Attach it to your Intelligence Configuration.

### Custom GenAI operator

For more specific scoring, write a custom operator with your own JSON schema. Example:

```json
{
  "displayName": "Products Discussed",
  "outputFormat": "JSON",
  "prompt": "Analise a transcrição. Identifique os produtos discutidos e o nível de interesse demonstrado.",
  "outputSchema": {
    "type": "object",
    "properties": {
      "products_discussed": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "product": { "type": "string" },
            "interest_level": { "type": "string", "enum": ["alto", "medio", "baixo"] }
          }
        }
      }
    }
  }
}
```

**Schema rules** (will silently break you if violated):
- Don't include `required` arrays — Twilio auto-marks everything required.
- Max 100 properties, 5 nesting levels, 8800 char output cap.
- Avoid `minLength`, `pattern`, `format`, `minimum` — these are unsupported and silently ignored.

### Logs and traces

Your server logs (pretty-printed by `pino-pretty`) show:
- Every inbound message
- Every LLM turn (prompt + response)
- Every tool call (name + args + result)
- Every outbound message

For deeper debugging: `VOICE_STREAM_DEBUG=true` taps the voice streaming pipeline (raw provider output + post-buffer output).

### Checkpoint

End a conversation. Open Twilio Console → CI → Conversations. See the Summary + Sentiment outputs. (Bonus: see a Script Adherence result if you configured one.)

## Chapter 8 — Where to go from here

You've shipped a working agent. The natural next steps:

### Custom tools

Anything the agent should do beyond KB search + handoff. Examples:
- Look up an order status from your CRM
- Schedule an appointment via a calendar API
- Send a payment link (Pix, Stripe, etc.)
- Update a contact in your CRM
- Trigger a webhook to your own system

Pattern: use `defineTool` (TS) or write a Custom Component (Langflow). The shape is in [Chapter 3](#chapter-3--wire-your-first-tool-kb-search).

### Deployment

The template ships with a Dockerfile and `fly.toml` aimed at Fly.io. The key constraints:
- **Region must be `iad`** (us-east-1) — Twilio's ConversationRelay is hosted there.
- **`auto_stop_machines = "off"`** — voice can't tolerate cold start.
- **`min_machines_running = 1`** — same reason.

See `DEPLOYING_AGENTS.md` for the full deployment guide.

### If you're going to demo this

Three things to rehearse before showing a customer:
1. **The first 30 seconds.** Agent greets by name, references prior context. This is the moment that lands.

## Appendix A — Starter kits in detail

## Appendix B — Stuck? Common issues

### Setup-phase issues

**`npm run dev` errors with `Cannot find module 'twilio-agent-connect'`**
- Run `npm install`. If you cloned the template recently, the workspace symlink to `solutions/conversation-relay-tac` needs to be rebuilt.

**Server starts but WhatsApp messages don't reach it**
- Check your WhatsApp Sender's webhook URL points at your ngrok URL or your deployed app, not localhost.
- Check ngrok is running (`ngrok http 3000`) AND the URL matches what's in the Console.

**`Server error: TWILIO_CONVERSATION_CONFIGURATION_ID is not set`**
- Your `.env` is missing the config ID. Get it from Twilio Console → Conversation Orchestrator → Configurations.

### Prompt-phase issues

**Agent ignores my prompt changes**
- Make sure `tsx watch` is running (the dev script does this by default). If you're running with `npm run start` (compiled), you need to rebuild.
- For Langflow: did you click Save in the Prompt component? Did you Save the flow?

**Agent says "Sou apenas um modelo de linguagem"**
- Your persona section is too weak. Strengthen it: "Você é Marina, da ACME, e só atende temas de ACME."

### Tool-phase issues

**Tool I wired never fires**
- Check the tool name in your prompt matches the tool name in the wiring EXACTLY. Case-sensitive.
- Check the tool description has concrete trigger words ("para X, Y, Z") not vague ones ("when relevant").
- Try a more specific prompt: "Para essa pergunta, chame search_X_kb." If it fires now, your tool description is the problem.

**Tool fires but returns an error**
- Look at the response body in the logs — not just the status code. The Twilio API tells you what's wrong.
- Common: wrong KB ID, wrong account, expired API key, wrong base URL.

### Memora issues

**`Trait not registered for this service: Contact.X`**
- The trait name doesn't match the schema. Inspect the schema:
  ```
  curl -u "$TWILIO_API_KEY:$TWILIO_API_SECRET" \
    "https://memory.twilio.com/v1/ControlPlane/Stores/$STORE_ID/TraitGroups"
  ```
- Use the EXACT field name from the schema (often camelCase: `firstName`, not `name`).

**Observation I just wrote isn't recalled**
- Read-after-write lag is real (0.5-3s). If you wrote and immediately tried to read in the same agent turn, the index hasn't caught up.
- Fix: poll for visibility before returning OR pass state via the tool's return value instead of a Memora roundtrip.

### Handoff issues

**Handoff tool fires but no Studio execution**
- Wrong `TWILIO_STUDIO_HANDOFF_FLOW_SID`, OR the Flow's REST trigger isn't enabled, OR the API key doesn't have the right scope.

**Studio executes but Flex task has no context**
- Missing `HandoffData.attributes`. The TAC OOTB tool fills `attributes` automatically — if you wrote a custom handoff tool, make sure you're passing `attributes` too.

### Voice issues

**Voice connects but the agent doesn't speak**
- Check the ConversationRelay WebSocket URL in your TwiML — should be `wss://<TWILIO_VOICE_PUBLIC_DOMAIN>/ws`.
- Check `TWILIO_VOICE_PUBLIC_DOMAIN` has NO protocol and NO path (just `your-app.fly.dev`).

**Voice latency feels high**
- Make sure you're deployed in `iad` (us-east-1). Other regions add perceptible RTT.
- Enable `MEMORY_RECALL_MODE=first-prompt` — pre-fetches memory on ConversationRelay setup event, saves 400-1000ms on first turn.

### When all else fails

- Read `CLAUDE.md` — it's the comprehensive gotchas list.
- Check the logs verbosely: `LOG_LEVEL=debug npm run dev`.
- Reset state: close any open conversations, run your cleanup script, restart the server.
